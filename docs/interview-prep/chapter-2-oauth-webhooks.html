Chapter 2

🐦 The Pigeon — OAuth & Webhooks

GitHub OAuth Authorization Code flow · HMAC-signed webhooks · fire-and-forget queueing

Memory anchor

A homing pigeon carries a sealed message, and only a sealed message with the right seal is trusted.

The wax seal on the message is the HMAC-SHA256 signature GitHub attaches to every webhook — if the seal doesn't match, the message is rejected without even being read. The pigeon flying out and back is the OAuth redirect dance: the browser is sent away to GitHub and comes back carrying a code. And the pigeon dropping the message and immediately flying off again is the webhook handler returning 200 right away instead of waiting around for the slow part to finish.

Block diagram

Webhook intake
The response to GitHub is decoupled from the actual AI review — the pipeline continues in the background after the handler already replied.

Easy

What OAuth flow does this use?

Standard Authorization Code flow: redirect the user to GitHub's /login/oauth/authorize, GitHub redirects back with a code, the backend exchanges that code server-side for an access token. The token never touches the browser directly during that exchange.

How does the backend know a webhook payload really came from GitHub?

HMAC-SHA256 signature verification. GitHub signs the raw request body with a shared secret and sends it as X-Hub-Signature-256. The backend recomputes the HMAC over the same bytes and compares with hmac.compare_digest — constant-time, not ==, specifically to avoid timing attacks.

Why does the webhook handler return 200 before the review finishes?

GitHub expects a fast response and will retry — and eventually disable — a webhook that times out. queue_review() just fires asyncio.create_task and returns; the actual review runs independently.

Medium

What security property does compare_digest actually buy you over ==?

Python's == on strings short-circuits at the first mismatched byte, so comparison time leaks how many leading bytes matched. An attacker measuring response timing precisely enough could recover the correct signature one byte at a time. compare_digest always takes the same time regardless of where the mismatch is, so there's no timing signal to exploit.

The handler fires an unawaited asyncio.create_task. What if it raises?

Left unhandled it'd be swallowed as an "exception never retrieved" warning and the PR would silently stay PENDING forever. That's why the worker wraps the whole pipeline in try/except and self-reports failure into the database (and, since Chapter 4, over the WebSocket) — fire-and-forget from the webhook handler's side, but not silent about failure.

Why store the GitHub access token on the User row?

It's what's used to call the GitHub API on the user's behalf later — fetch diffs, post review comments. The trade-off is a long-lived token sitting in the primary database rather than a secrets manager; for real production you'd want it encrypted at rest or moved out, the same way Chapter 6's Terraform does for the app's own secrets but not (yet) for user tokens.

Challenge

Situation → Solution → Trade-off → Benefit
Webhook delivery is at-least-once, not exactly-once
Situation
GitHub retries webhooks that don't get acknowledged fast enough or that fail. A naive handler would create a duplicate PR row — or trigger a duplicate, token-burning AI review — every time the same event got redelivered.
Solution
The handler looks up the existing PullRequest by github_pr_id (which has a unique constraint) before deciding whether to insert or update.
Trade-off
Every webhook event does a DB read before any write, adding a small amount of latency to a path that's already trying to be fast for GitHub's sake.
Benefit
Idempotency — replaying the same event any number of times converges to the same DB state instead of piling up duplicate reviews.
