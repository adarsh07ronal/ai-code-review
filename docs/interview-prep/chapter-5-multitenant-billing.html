Chapter 5

🐜 The Ant Colony — Multi-Tenant, RBAC & Billing

Organization / OrganizationMember / OrgRole · dependency-based RBAC · Stripe Checkout & webhooks

The schema existed since Chapter 1 with zero endpoints and zero enforcement — this phase wired it up.

Memory anchor

An ant colony has exactly one queen, a caste of soldiers, and workers who follow orders — never the reverse.

The queen is the org OWNER — there's always exactly one, and nothing in the API lets you create a second one or demote her. Soldier ants are ADMINs — they can guard the colony (invite/remove members) but don't run it. Worker ants are plain MEMBERs — they can see the colony's stores but can't reorganize it. And the colony itself, gathering food to survive, is the org's Stripe subscription — billing keeps the whole colony fed.

Block diagram

Two lanes: RBAC + Billing
RBAC and billing don't touch each other directly — RBAC gates who can act inside an org, billing decides what tier a user is on.

Easy

What are the three roles and what can each do?

OWNER, ADMIN, MEMBER. Owner and admin can invite/remove members and change roles; members can only view. An owner's role can never be changed or removed via the API — every mutating endpoint explicitly blocks that, so an org can't accidentally end up without an owner.

How does Stripe Checkout know which plan the user picked?

The tier is attached as metadata on the Checkout Session and on subscription_data.metadata. Stripe copies that onto the resulting Subscription, so both the initial webhook and any later plan-change webhook carry the tier directly — no separate lookup needed.

What's the Stripe customer portal, and why not build a custom "cancel subscription" page?

Stripe's hosted billing portal handles plan changes, cancellation, and payment method updates without the app needing to build or PCI-scope any of that UI itself.

Medium

Why carry the tier in metadata instead of mapping Stripe price IDs back to tiers?

An inverse map (price_xyz → "pro") has to be kept in sync by hand every time a price changes in the Stripe dashboard, and silently goes stale if forgotten. Metadata is set once, at Checkout creation, from the same tier the endpoint already validated — no second source of truth that can drift from the first.

What actually stops a plain member from inviting someone?

require_org_role is a dependency factory — it depends on get_org_membership (which 403s outright if the caller isn't a member at all), then checks the role against an allow-list. FastAPI resolves this before the endpoint body runs — a member never reaches the invite logic. Verified directly: registered a fresh user as a plain member, confirmed their own invite attempt came back 403.

What stops someone from inviting a new member directly as owner?

An explicit check in the invite endpoint rejects role == OWNER. Combined with the role-update endpoint also refusing to touch an existing owner, there's exactly one way to become an owner — creating the org — and no way to make someone else one afterward through this API. Deliberate simplification, not an oversight.

Challenge — the best "tell me about a bug" story

Situation → Solution → Trade-off → Benefit
A pre-existing auth-guard race condition, found while verifying an unrelated feature
Situation
While manually verifying the new billing/team pages, a full browser refresh on any dashboard page intermittently bounced a logged-in user straight back to login — even with a perfectly valid token in localStorage.
Root cause
The auth store's loading flag started as false. The redirect effect — if (!loading && !user) router.replace("/auth/login") — ran on mount using that initial state, before the async user-fetch had a chance to resolve and flip loading to true. A classic React effect-ordering race: two effects fire in the same commit, one kicks off an async check, the other reads stale state from before that check started.
Solution
Added an explicit checked: boolean to the auth store, set true only once the user-fetch has actually completed — success or failure. The guard changed from !loading && !user to checked && !user — it now waits for a definitive answer instead of racing an in-flight request.
Trade-off
One more piece of state to keep in sync, and every page using the guard pattern had to be updated in lockstep — a missed page would still have the bug.
Benefit
This pattern was copied into two brand-new pages from the original dashboard page — fixing it once at the store level, instead of patching each page's local effect logic, meant all three pages (and any future page reusing the guard) got the fix for free.

Why this is worth bringing up: it wasn't something the task asked for — it surfaced during manual verification of an unrelated feature, and shipping without noticing it would have meant landing a subtly broken login experience.
