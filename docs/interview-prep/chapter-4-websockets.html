Chapter 4

🐝 The Bee — Real-Time WebSockets

FastAPI WebSocket · Redis pub/sub fan-out · exponential-backoff reconnect

This is the feature I actually built to close the "real-time review delivery via WebSockets" gap in the original resume bullet.

Memory anchor

One bee finds the flower; the whole hive knows within minutes.

A single bee doesn't fly back to tell every other bee individually — it dances at the hive, and every bee near the hive picks up the signal. That hive is Redis: when any backend replica finishes a review, it doesn't try to remember which browser socket to push to — it just "dances at the hive" (publishes to Redis), and whichever replica is actually holding that browser's connection picks it up and delivers it.

Block diagram

Cross-replica fan-out
This works identically with one replica or fifty — nothing in the app has to know or care how many backend tasks are currently running.

Easy

Why WebSockets instead of polling?

A review can take anywhere from a few seconds to over a minute. Polling means either hammering the API every couple seconds — wasteful, and adds load right when the backend is already busy running the AI pipeline — or a noticeably laggy UI. A push means the dashboard updates the instant a stage finishes, no interval to tune.

How does the frontend authenticate the WebSocket connection?

The JWT access token is passed as a query parameter: /api/v1/ws/reviews?token=<jwt>. Browsers can't attach custom headers to a WebSocket handshake, so query param is the standard workaround. The server decodes it the same way as any other endpoint and closes the socket with code 1008 if it's invalid.

What happens on the frontend if the connection drops?

Automatic reconnect with exponential backoff — starts at 1s, doubles up to a 15s cap. Not instant-retry-in-a-loop (hammers the server during an outage), not no-retry-at-all (user has to manually refresh).

Medium

Why does a naive in-memory connection dict break once you run multiple replicas?

If a review finishes on replica A, but the client's socket is connected to replica B, an in-memory dict on replica A has no way to reach that client — it doesn't even know the connection exists. Every publish goes through Redis instead; every replica subscribes and dispatches to whichever locally-connected sockets match that user id.

Why publish through Redis unconditionally, even in a single-replica dev setup?

Two reasons: it's the same code path in dev and production, so there's no "works locally, breaks in prod" surprise the first time it runs behind two ECS tasks. And Redis was already a hard dependency, so this reuses existing infrastructure instead of building two different connection-manager implementations gated behind an environment flag.

Chapter 6's ALB uses sticky sessions for the backend. Why, if Redis pub/sub already solves fan-out?

Redis solves "which replica needs to deliver this event" — it doesn't change that a WebSocket is a long-lived TCP connection pinned to whichever replica accepted it. Sticky sessions plus a generous deregistration delay protect against ECS killing an old task mid-deploy and abruptly cutting active connections, instead of letting them drain.

Challenge

Situation → Solution → Trade-off → Benefit
You can't just curl a WebSocket to verify it works
Situation
There was no live GitHub webhook flowing through the dev stack to trigger a real review and prove the event actually reaches the browser.
Solution
Published a fake event directly onto the Redis channel from the CLI and watched it show up live in the dashboard. This exercises the exact same code path the review worker would use — the listener doesn't know or care whether the publish came from the app or a raw CLI command.
Trade-off
Proves the transport (Redis → backend listener → WebSocket → UI) works, but doesn't exercise the real trigger path from an actual GitHub webhook through the AI pipeline — that needs a real OpenAI key and a real webhook delivery, neither available in this environment.
Benefit
Fast, deterministic, repeatable verification of the part of the system that was actually new and risky — multi-replica fan-out — without being blocked on external services out of scope to configure.
