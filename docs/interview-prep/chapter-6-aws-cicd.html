Chapter 6

🐙 The Octopus — AWS ECS & CI/CD

Terraform · ECS Fargate + ALB · target-tracking auto-scaling · OIDC · split CI/CD/deploy

Written as Terraform + GitHub Actions and validated locally — no live AWS account, so nothing here has actually been deployed. Say that up front if asked.

Memory anchor

An octopus has one brain and eight independent, coordinated arms — and can regrow one that's lost.

The arms are ECS Fargate tasks — independent workers that can grow in number when there's more to grab (auto-scaling) and shrink back down when things are calm. The brain routing signals to the right arm is the ALB, deciding which task handles which request. And an octopus regenerating a lost arm is exactly what the deployment circuit breaker does — a failed task gets replaced automatically instead of leaving a gap.

Block diagram

Build → gate → deploy
Building and pushing an image is automatic and low-risk. Rolling it out to production is a deliberate, separate, human-triggered step.

Easy

Why ECS Fargate instead of EKS or plain EC2?

Fargate is serverless containers — no EC2 instances or Kubernetes control plane to patch and manage. For a project this size, Kubernetes' extra flexibility isn't needed, and it comes with real operational overhead not worth paying for two services and a straightforward scaling story.

What's the auto-scaling actually scaling on?

Three target-tracking policies on the backend: CPU (60%), memory (75%), and ALB requests-per-target (1000). Frontend just scales on CPU — it's a stateless server with no long-lived connections.

Why does the backend get a third scaling metric the frontend doesn't?

Because of the WebSocket work in Chapter 4 — a burst of concurrent long-lived connections can tie up backend task capacity without spiking CPU or memory (a connection can just be idle). Request-count-per-target catches that kind of load CPU/memory alone would miss.

Medium

How do secrets get into the running containers?

AWS Secrets Manager, not plain environment variables in the task definition. The execution role has an inline IAM policy scoped to exactly one secret ARN, and the container definition references each key with valueFrom — ECS resolves it at container start, so values never appear as plaintext in the task-definition JSON the way a plain environment block would.

A subtle one — does setting NEXT_PUBLIC_API_URL as an ECS runtime env var actually work?

No. Next.js inlines any NEXT_PUBLIC_* variable into the client bundle at build time — by the time the container is running, the static output is already compiled. The real fix is in the Dockerfile: ARG NEXT_PUBLIC_API_URL in the builder stage, set before npm run build, passed in by the CD workflow as --build-arg. Caught this before it became a "works in Terraform plan, breaks in prod" surprise.

Why is deploy.yml manual instead of running automatically on merge, when cd.yml isn't?

Building and pushing an image to ECR is low-risk and easily reversible — just an artifact sitting in a registry. Actually rolling that image out to ECS is a different risk category — kept as a manual workflow_dispatch trigger so a production infra change is always a decision, not an automatic side effect of a merge. This came directly out of a review flagging an earlier draft that ran terraform apply -auto-approve on every push as contradicting the "no live deploy" scope.

Why OIDC instead of long-lived AWS access keys in GitHub Actions?

No access key/secret stored in GitHub Secrets at all — GitHub's OIDC token is exchanged for short-lived AWS credentials scoped to whatever IAM role trusts that specific repo/workflow. A long-lived key sitting in GitHub Secrets is a standing credential that works forever if leaked; OIDC credentials expire in under an hour and are scoped per workflow run.

Challenge

Situation → Solution → Trade-off → Benefit
No AWS account was available to actually validate the infrastructure
Situation
Terraform code that's never been run is worth very little — HCL that "looks right" can still fail on a real apply (circular dependencies, wrong argument names, provider quirks).
Solution
Ran terraform init -backend=false, then validate and plan with dummy variable values. Plan got as far as actually trying to talk to AWS and failed only on missing credentials — meaning every resource reference and the entire dependency graph resolved correctly; the only thing missing was real credentials.
Trade-off
Proves the configuration is internally consistent, not that it will provision successfully end-to-end — IAM permission boundaries, service quotas, or AZ availability can only surface on a real apply.
Benefit
Caught real mistakes before they'd have surfaced as a broken apply later — an invalid data source that doesn't actually exist in the AWS provider, and several formatting issues. Cheap to catch locally, much more annoying to debug against a live account mid-deploy.
Three feature branches built off master independently instead of stacked
Situation
WebSockets, billing/RBAC, and infra were all built as separate PRs, each branching from the same master baseline rather than from each other.
Solution
Keep them independent so none of the three PRs depends on another merging first — they can be reviewed and merged in any order.
Trade-off
Files touched by more than one branch (the dashboard page, touched by two of the three) will conflict when merging the second one — resolved by hand, not automatically.
Benefit
No branch is blocked waiting on another, and a reviewer can approve and ship just the WebSocket work without also signing off on the billing changes in the same review.

Cross-Cutting — whole-system questions

Walk me through end-to-end what happens when someone opens a pull request.

GitHub sends a webhook → HMAC verified → PR row upserted (idempotent) → background task fired, handler returns 200 immediately → worker marks REVIEWING and publishes that over the WebSocket → fetches diff → calls GPT-4o for structured findings → persists CodeReview → posts a Markdown comment back to GitHub → marks COMPLETED and publishes the final event → dashboard updates live, no refresh needed.

If this had to handle 10x the traffic tomorrow, what breaks first?

Two candidates: OpenAI rate limits — there's no queueing or concurrency cap, a burst of PRs could all hit the API at once. And the single NAT Gateway in the VPC — a documented cost trade-off, not an accident. I'd add a proper task queue before touching infra scaling, since that's the actual bottleneck, not compute capacity.

What's the most interesting engineering decision in this project?

The Redis pub/sub design for WebSockets — the one piece designed for a requirement (multi-replica auto-scaling) that didn't exist yet when it was built, and works identically at any replica count. Close second: keeping the deploy workflow manual instead of auto-applying — a guardrail that came directly out of a review catching scope creep, not something planned from the start.
