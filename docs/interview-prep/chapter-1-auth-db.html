Chapter 1

🐢 The Turtle — Auth & Database

FastAPI · SQLAlchemy 2.0 async · PostgreSQL · JWT (HS256) · bcrypt

Memory anchor

A turtle carries its home on its back and never rushes.

The shell is the hashed password — hard on the outside, protects the soft data inside, and you can never crack it open to see the original. The turtle's slowness is bcrypt being deliberately, adjustably slow, so brute-forcing a password is expensive on purpose. And the turtle carrying its house wherever it goes is the user's data always traveling with a signed JWT, not a session pinned to one server.

Easy

Why JWT instead of server-side sessions?

Stateless — no session store to keep in sync once you have multiple backend replicas (which this app does, behind the ALB in Chapter 6). The token carries the user id (sub claim) and an expiry; any replica can verify it without a shared session table.

Access token vs refresh token — why two?

Access tokens are short-lived (24h here) and sent on every request, so keeping them short limits the damage if one leaks. The refresh token (30 days) is only sent to /auth/refresh to mint a new access token, so it's exposed far less often.

Where are passwords hashed?

security.py, using passlib's CryptContext(schemes=["bcrypt"]). Bcrypt is deliberately slow (adaptive cost factor) to make brute-forcing expensive — the standard choice over something fast like SHA-256, which is the wrong tool for password storage.

What's CREDENTIALS_EXCEPTION?

A shared 401 raised for any auth failure — expired token, malformed token, wrong token type, user not found. Returning the same generic message for all of these is intentional: you don't want the API telling an attacker whether a specific account exists vs. whether their token is just malformed.

Medium

Walk me through what happens when a request hits a protected endpoint.

FastAPI's dependency injection resolves Depends(get_current_user). That pulls the Authorization: Bearer header, decodes it (verifies signature + expiry), checks payload["type"] == "access" so a refresh token can't be used as an access token, extracts sub as the user id, then loads the User row from Postgres. Every layer can fail with a 401/403 independently.

Why check the token type explicitly instead of trusting any valid signature?

Both token types are signed with the same secret and would both pass signature verification. Without the type check, a leaked refresh token (30-day lifetime) could be used directly as an API credential instead of only being exchangeable for a short-lived access token — that defeats the entire point of having two token types.

bcrypt has a 72-byte input limit. How is that handled here?

hash_password() explicitly checks the byte length and raises a 422 before it reaches passlib. Without this, bcrypt silently truncates the password — meaning a password plus anything past byte 72 all hash to the same value. A subtle bug because it doesn't error, it just quietly does the wrong thing.

The Organization tables existed since Phase 1 but weren't used until Phase 5. Why build schema early?

Judgment call, not a rule — it pays off when the shape is already well understood (an org has members, members have one of three roles) and low-risk to get right early. Phase 5 ended up mostly wiring endpoints and RBAC checks against a schema that was already correct, instead of designing + migrating + wiring in the same PR.

Challenge

Situation → Solution → Trade-off → Benefit
Async DB sessions and fire-and-forget background tasks don't mix safely
Situation
FastAPI's Depends(get_db) yields a session scoped to one HTTP request and closes it after. The AI review worker runs as a detached asyncio.create_task, outliving the request that triggered it — so it can't reuse the request-scoped session.
Solution
The worker opens its own session directly from AsyncSessionFactory() instead of going through the get_db dependency.
Trade-off
Two different session-acquisition patterns exist side by side in the codebase — a new contributor has to know why they're different, since it's not visually obvious that one runs inside a request lifecycle and the other doesn't.
Benefit
The background job's DB session lives exactly as long as the job does — no risk of a route handler's finally: await session.close() yanking the connection out from under a task that's still running.
