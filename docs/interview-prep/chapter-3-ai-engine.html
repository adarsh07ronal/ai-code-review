Chapter 3

🦉 The Owl — AI Review Engine

GPT-4o · structured JSON findings · GitHub PR comment formatting

Memory anchor

An owl doesn't just stare at the forest — it sees in a structured way: this branch, that shadow, this movement.

The owl's huge, precise eyes are the model reading the diff carefully. But an owl doesn't report back in vague hoots — it gives you a structured verdict: severity, file, line, suggestion. That's exactly why the AI is asked for structured JSON instead of a free-text paragraph — one clear judgment, not a mood.

Block diagram

Review pipeline
One AI call produces one structured payload — it branches into a persisted DB row and a formatted GitHub comment, instead of two separate model calls or fragile re-parsing.

Easy

Which model does this use, and why GPT-4o?

Good code-reasoning quality with lower latency/cost than the largest reasoning models — matters here because review latency directly affects developer experience. Nobody wants to wait three minutes for a PR comment.

What does the AI actually return — free text or something structured?

Structured JSON: summary, findings (file/line/severity/message/suggestion), security issues, architecture suggestions, overall quality. The worker counts severities out of that structure rather than parsing them out of prose.

Where does the review end up?

Two places: persisted as a CodeReview row in Postgres (so the dashboard can show history), and — if the repo's config allows it — formatted as Markdown and posted back as an actual GitHub PR review comment.

Medium

Why structured JSON instead of just asking the model to write a nice comment directly?

Two different consumers need two different shapes from the same review: the dashboard wants queryable severity counts, GitHub wants a nicely formatted comment. Structured JSON lets the comment be rendered from the same data that populates the DB counts — one AI call, two presentations, instead of calling the model twice or fragile-parsing a comment string back into structured data.

What happens if posting the GitHub comment fails — does the whole review fail?

No — it's wrapped in its own try/except, separate from the outer pipeline try/except. A GitHub API hiccup logs a warning but doesn't roll back the CodeReview row already persisted, and doesn't flip the PR to FAILED. The review itself succeeded; only "tell GitHub about it" didn't, and that's a meaningfully different failure.

Any concerns with how severities are counted from the findings list?

It's a few passes over a combined list for three severity buckets — fine at the size these lists actually are (a PR review producing thousands of findings would be useless to a human anyway). Worth mentioning if asked to nitpick, not worth "fixing" pre-emptively given how small the list realistically is.

Challenge

Situation → Solution → Trade-off → Benefit
LLM output isn't guaranteed to match your schema
Situation
Even when asked for JSON, a model can occasionally return malformed output, omit a field, or use an unexpected severity string.
Solution
The code defensively uses .get() with defaults everywhere it reads from the AI response, instead of direct dict indexing — a missing field degrades gracefully (empty list, default severity) rather than throwing mid-pipeline.
Trade-off
You lose an immediate, loud failure if the model's output format drifts — a KeyError would tell you fast; silent defaulting could mask a real prompt-quality regression until someone notices reviews look thinner than expected.
Benefit
One malformed AI response doesn't take down the whole pipeline or leave a PR stuck in REVIEWING — worse review quality is a much better failure mode than a 500.
